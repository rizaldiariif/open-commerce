Muse Commerce · Single-Brand MVP Plan

White-label ecommerce, delivered as one fork/deployment per brand

This document captures the agreed product scope, architecture decisions, data model, user flows, and implementation phases for a plain single-brand ecommerce app built with TanStack Start, Convex, Convex Auth, Convex File Storage, Xendit, and transactional email.

TanStack Start Convex Convex Auth Convex File Storage Xendit Vercel

1. Product summary

Muse Commerce is a single-brand ecommerce application. Each brand receives its own fork or deployment, so the app does not need multi-tenant routing, tenant isolation, tenant-level billing, or in-app custom domain management for the MVP.

MVP promise: a brand can manage products and content, customers can log in and place paid orders, admins can manage inventory and orders, payment is handled through Xendit, shipping is tracked manually with an airwaybill number, and customers receive email notifications.

4. Email provider options

The MVP needs transactional email for invoices and order notifications. The implementation should hide provider-specific logic behind a small internal email module so the provider can be changed later.

Provider Best for Notes
Resend recommended MVP Fast developer experience and simple transactional email. Good default choice for a new app. Easy API, straightforward setup, and works well with React-style email templates if desired.
Postmark High-quality transactional email deliverability. Strong option if reliability and transactional-only email are the main priorities.
SendGrid Broad email platform features and larger ecosystem. Powerful but may be heavier than needed for MVP transactional emails.
Mailgun Developer-oriented email sending and domain control. Good option if the team already uses it or wants flexible email APIs.
Amazon SES Low-cost high-volume sending. Cost-effective but has more setup and operational overhead than the simpler providers.
Recommendation: use Resend for the MVP unless there is an existing provider preference. Keep the email module provider-agnostic so Postmark, SendGrid, Mailgun, or SES can be swapped in later.

6. Core user flows

Customer checkout flow

  1. Customer registers or logs in.
  2. Customer adds products/variants to cart.
  3. Customer opens checkout and confirms shipping/contact details.
  4. System validates stock and coupon eligibility.
  5. System creates order with pending_payment order status and unfulfilled fulfillment status.
  6. System deducts inventory immediately in the same Convex mutation that creates the order, using inventory movement records to prevent overselling.
  7. System reserves coupon redemption against the pending order if a coupon is used.
  8. System creates Xendit invoice and stores invoice URL/reference.
  9. If Xendit invoice creation fails, system marks the order as payment_failed, restores inventory, releases coupon reservation, and shows a retryable checkout error.
  10. System schedules expiry using the editable setting, default 1 hour.
  11. System sends invoice email.
  12. Customer pays through Xendit.
  13. Xendit webhook confirms payment and updates the order/payment status.
  14. System sends payment confirmation email.

Pending payment expiry flow

  1. Use a Convex scheduled function per order via scheduler.runAfter, plus a periodic cleanup job as a safety net for missed or delayed expiries.
  2. If order is still pending_payment, mark payment as expired.
  3. Mark order as payment_failed. Reserve cancelled for customer/admin cancellation before payment or admin cancellation after review.
  4. Restore inventory using inventory movement records.
  5. Release any pending coupon reservation.
  6. Send payment expired email.

Manual shipping flow

  1. Admin opens a paid order.
  2. Admin marks fulfillment as processing when preparing the package.
  3. Admin enters courier name and airwaybill number.
  4. Admin clicks submit/mark as in delivery.
  5. System creates or updates shipment record.
  6. System changes fulfillment status to in_delivery.
  7. System sends shipment email to customer.
  8. Admin can later mark fulfillment as delivered.

Xendit webhook flow

  1. Verify the Xendit webhook token/signature before reading the payload.
  2. Find the payment by Xendit invoice ID or external ID.
  3. Ignore duplicate events that have already been processed.
  4. Reject or flag events where amount, currency, or order reference does not match the stored payment.
  5. Map paid/settled events to payment paid and order paid.
  6. Map failed events to payment failed and order payment_failed, then restore inventory and release coupon reservation.
  7. Map expired events to payment expired and order payment_failed, then restore inventory and release coupon reservation.

Important model notes

  • siteSettings should include store name, logo, favicon, support email, SEO fields, free-shipping setting, and editable pending payment expiry minutes.
  • siteContent should store fixed-layout editable content such as hero title, hero subtitle, hero image, about text, footer text, and homepage banners.
  • productVariants should support flexible attributes such as size, color, flavor, package size, or other plain ecommerce options.
  • inventoryMovements should be append-only where possible so stock deductions/restorations are auditable.
  • customerAddresses should store recipient name, phone number, address lines, city, province/state, postal code, and optional notes.
  • orders should snapshot customer contact, shipping address, line item names/prices, discount, totals, order status, fulfillment status, and expiry timestamp so historical orders are stable even if products change later.
  • payments should store Xendit invoice identifiers, invoice URL, amount, status, and webhook metadata.
  • shipments should store courier name, airwaybill number, shipping status, shipped date, delivered date, and admin user reference.
  • adminActivityLogs should record important admin actions such as order status changes, shipment updates, manual refunds, inventory edits, and settings changes.
  • emailEvents should record attempted/sent/failed notifications for debugging.
  • Convex Auth should create the first superadmin through a one-time seed or bootstrap mutation guarded by a setup token environment variable. After the first superadmin exists, bootstrap must be disabled.
  • Media assets should use soft deletion by default. Old product/content images can be hidden from the UI immediately, then cleaned up later by an admin-only maintenance job after confirming they are no longer referenced.

9. Coupon MVP scope

Coupons are included in the MVP, but should stay simple.

  • Coupon code.
  • Fixed discount amount.
  • Percentage discount.
  • Minimum order amount.
  • Maximum discount cap for percentage coupons.
  • Usage limit.
  • Per-customer usage limit, optional.
  • Active date range.
  • Enabled/disabled status.

Coupon usage should be reserved when a pending order is created, consumed when payment becomes paid, and released if payment fails, expires, or the order is cancelled before payment.

Out of scope for MVP: stackable coupons, product/category-specific coupon rules, buy-X-get-Y, customer segment targeting, and automatic campaigns.

13. Key risks and design notes

Inventory locking risk: stock is deducted when the order is created. If a customer does not pay, the product can remain unavailable. The 1-hour editable expiry job is mandatory for the MVP, not optional.

Other notes

  • Keep payment secrets and email provider API keys in environment variables, not editable admin fields.
  • Make Xendit webhook handling idempotent so duplicate webhooks do not double-update orders or inventory.
  • Store raw webhook metadata or event IDs for debugging, but avoid storing unnecessary sensitive data.
  • Use append-only inventory movements where possible so stock corrections can be audited.
  • Keep email sending behind a provider abstraction to allow switching providers later.
  • Because this is single-brand, adding multi-tenant support later should be treated as a separate migration project.
